## 0. 关键结论（先读）

1. **数据库结构已 100% 找回**：从二进制抽出的 001–018 迁移 SQL 在空库上顺序重放，得到的 139 个对象（表/索引/触发器）与 live 库 `.schema` **逐条一致**。重建不需要猜 schema，live 库可以直接被新代码接管。
2. **Rust/前端业务代码丢失**：Fox 独有的 **52 个 Tauri 命令**、**22 张表**的读写逻辑、全部前端页面（投喂/工具卡/场景/矩阵/决策/备份/健康/AI 任务中心/AI 助手配置）需重写。fork b496428 只保留了 v1.1.2 阶段的 9 个提交（身份隔离、阅读状态、设置页等）。
3. **MCP 服务端 JS 已完整找回**（db/safe/core/mcp/server 五个模块，可读源码），可几乎原样复用。
4. **迁移编号冲突是最大风险**：upstream 的 002/003（embedding）与 Fox 的 002/003（upstream_v120 / ai_task_center）同号不同名，upstream 的 `INSERT OR IGNORE` 会被静默吞掉；且 upstream `migrate()` 无版本门控、每次启动全量重跑。方案：**以 Fox 001–018 为正史，upstream 002/003 改编为 Fox 019/020**（草案已生成并验证）。
5. **合并难度可控**：试合并 upstream HEAD ← fork/fox-product-lab，冲突 12 个文件 / 23 个 hunk（storage.rs 7、settings.tsx 6，其余各 1）。

## 2. 迁移冲突分析与对账策略

### 2.1 事实
- Fox live：`schema_migrations` 001–018（001–014 于 2026-07-11 20:26 一次性写入，015 7-11 22:35，016 7-12 10:41，017 7-12 16:12，018 7-12 18:45，均北京时间）。
- Fox 001 + 002 的表集合 = upstream 001 的表集合（仅 `annotations.read_status` CHECK 更宽，Fox 8 值 ⊃ upstream 3 值）。
- Fox 004 给 `repo_ai_documents` 加了 6 列；upstream 没有，但 upstream 代码不读它们，兼容。
- upstream 002 `embedding_invalidation`（11 个 invalidate 触发器）、003 `embedding_dirty_queue`（表 + 2 索引 + 11 个 queue 触发器）在 Fox 库中**不存在**。
- upstream `migrate()`：每次启动执行 001/002/003（全 IF NOT EXISTS + INSERT OR IGNORE），再校验 `REQUIRED_SCHEMA_COLUMNS` 与 `version='001' AND name='initial_schema'` 标记；**无版本门控、无备份**。
- Fox 原 runner（二进制字符串可见）：按版本顺序执行、每个迁移前 `SELECT COUNT(*) FROM schema_migrations WHERE version='0NN'` 门控、迁移前强制备份（`*_pre-migration`）、启动时 `SELECT COUNT(*) … WHERE version IN ('002'..'018')` 校验完整性；010/annotations 重建在 `BEGIN IMMEDIATE` 内执行。

### 2.2 风险
| 风险 | 后果 |
|---|---|
| 直接用 upstream migrate() 打开 Fox 库 | 002/003 标记被吞（库里写着 upstream_v120/ai_task_center，代码以为 embedding 已迁），trigger 虽建成但版本记录失真；以后任何按版本判断的逻辑都会错 |
| upstream 未来新增 004/005… | 与 Fox 004–018 同号，`INSERT OR IGNORE` 再次静默跳过，**真实 SQL 可能被当成已执行** |
| 照 CLAUDE.md 旧说法“删库重建幂等 001” | 直接丢失全部数据（评审 P0-2） |
| upstream `clear_local_database` / legacy 文件删除 | 误删；需确认只作用于 dev 数据目录 |

### 2.3 策略（定稿）
1. **Fox 001–018 冻结为正史**，文件放 `packages/storage/migrations/fox/0NN_*.sql`（本目录 `migrations/` 已就绪，已验证与 live 一致）。
2. **upstream 迁移一律“改编导入”**：upstream 每出一个迁移，Fox 新建下一个编号，名字加 `upstream_` 前缀，去掉 upstream 自带的 schema_migrations 写入。当前：`019_upstream_embedding_invalidation.sql`、`020_upstream_embedding_dirty_queue.sql`（草案在 `migrations/proposed/`，已在 018 结构上重放通过）。
3. **Runner 规则**：`migrations: &[(version, name, sql)]` 静态表；启动时读 `SELECT version,name FROM schema_migrations`；
   - 已有版本但 name 不符 → 拒绝启动并提示（防止编号撞车被吞）；
   - 有待执行迁移 → 先 `VACUUM INTO`/文件复制备份 + 校验 `PRAGMA integrity_check`，失败则不迁移；
   - 每个迁移单独 `BEGIN IMMEDIATE … COMMIT`，SQL 内写 `INSERT INTO schema_migrations`（不用 OR IGNORE）；
   - 全新空库：顺序执行 001→最新（不再有“幂等大 001”）。
4. upstream 的 `REQUIRED_SCHEMA_COLUMNS` 保留作为启动后自检，但标记检查改为“最新 Fox 版本存在”。
5. embedding 首次启用时对存量 492 仓库做一次全量入队（或调用 `rebuild_vector_index`），不靠触发器补历史。
6. 重写 CLAUDE.md 迁移章节：禁止删库；新增迁移流程 = 新编号文件 + runner 表 + 对 live 副本的回归测试。
