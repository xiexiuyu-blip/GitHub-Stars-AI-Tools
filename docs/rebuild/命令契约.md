# 命令契约与协作规则

适用于所有 AI 开发者（Grok、Codex）和总控（Claude）。Fox 不需要读这份。2026-10-03 起生效。

## 1. 角色与顺序

| 谁 | 做什么 |
|---|---|
| Fox | 里程碑时亲手验收；只做只有他能做的事：输入电脑密码、钥匙串授权、粘贴令牌、批准 AI 试跑预算、点头切换正式库 |
| Claude（总控） | 写任务卡、建工作区、派发、审核、合并、向 Fox 汇报；Grok 做不了的、额度用完后剩下的，由 Claude 接手；最后一期收尾 |
| Grok（主力开发） | 按任务卡写代码和测试，交回报告 |

**Fox 定的顺序（2026-10-03）**：Grok 先开发，直到它本周额度用完；没开发完的由 Claude 接手；Grok 解决不了的问题，由 Claude 最后一期收尾。

## 2. Git 规则（Fox 2026-10-03 同意，只限本仓库）

- 只在本机：**不推送**、不改 remote、不打 tag、不开 PR。`origin` 指向 Fox 的 GitHub 分叉，也不要往里推。
- **两条线**：`fox-rebuild` 是 Fox 的开发版在跑的分支（主工作区），只在总控确认过的时间点更新（`tools/cards/release.sh`，一次发布只让开发版重新编译一次，也就只弹一次钥匙串授权）；`fox-integration` 是总控的集成线，每张卡审核通过后先合并到这里（在 `../fox-stars-lab-wt/_integration/` 里，用 `tools/cards/merge-card.sh`，任何一步失败都停下）。
- 每张任务卡一个分支 `card/<卡号-短名>`（基于 `fox-integration`），在独立工作区 `/Users/fox/WorkSpace/_external_tools/fox-stars-lab-wt/<卡号-短名>/` 开发（用 `tools/cards/new-card.sh` 建）。
- **只有总控能运行 git 写命令。** 开发者在工作区里只许 `git status|diff|log|show`。总控审核通过后在卡分支上提交，再 `git merge --no-ff` 合并进 `fox-rebuild`。提交信息以 `卡NN：` 开头，结尾带 `Co-Authored-By`。
- 合并后发现问题：`git revert -m 1 <合并提交>`，不改写历史（不 force，不 `reset --hard` 主线）。
- 主工作区（`fox-stars-lab/`）是 Fox 的 dev 版在跑的地方。**只有总控发布后它才会变**，没审核的代码不会出现在那里。

## 3. 一张卡的生命周期

1. 总控写卡 `docs/rebuild/任务卡/<卡号-短名>.md`（头部有「允许改动」清单，正文有「验收」），提交到主线。
2. `tools/cards/new-card.sh <卡号-短名>`：建分支和工作区。
3. `tools/cards/dispatch.sh <卡号-短名>`：后台派发给 Grok。三层保护：内核沙盒（只能写工作区；正式库、开发库、钥匙串和各类凭据读写都被内核禁止）、禁令清单（git 写命令、联网下载、杀进程、装依赖等被拦截，只返回错误，不会中止任务）、干净环境（不继承总控会话里的令牌和变量）。
4. Grok 交回 `.card-report.md`。
5. 总控审核（见 §7），先跑 `tools/cards/check-scope.sh <卡号-短名>` 核对改动是否都在卡里的「允许改动」内，越界的还原。通过：提交并合并。退回：写修改意见，`dispatch.sh <卡号-短名> <意见文件>` 续作。
6. 合并后总控在 Fox 的 dev 版里实际点一遍并截图，有问题就回退。
7. 一片（里程碑）做完，才请 Fox 亲手验收。

状态表在 `docs/rebuild/任务卡/README.md`。每次派发，总控都会告诉 Fox 派了什么、用的是 Grok 额度。

## 4. 允许的命令（在工作区根目录执行）

| 命令 | 作用 |
|---|---|
| `tools/cards/run.sh web-build` | 前端类型检查 + 打包（`pnpm build`） |
| `tools/cards/run.sh web-test [过滤词]` | 前端测试（vitest） |
| `tools/cards/run.sh rust-fmt` | 检查 Rust 格式（`--check`） |
| `tools/cards/run.sh rust-fmt-fix` | 自动整理 Rust 格式 |
| `tools/cards/run.sh rust-check` | Rust 编译检查 |
| `tools/cards/run.sh rust-test [测试名过滤]` | Rust 测试（`--lib`）。会跳过 1 个必须访问系统钥匙串的用例（沙盒里没有钥匙串，它必然失败），总控审核时在沙盒外跑完整套件 |
| `git status` / `git diff` / `git log` / `git show` | 只读 |
| 读文件、搜索 | 整个仓库；被沙盒禁止的位置读不到 |
| 写文件 | 沙盒只允许写工作区；逻辑上只许改任务卡「允许改动」里的路径，外加 `.card-report.md`，越界由总控事后核对并还原 |
| 普通文件和文本命令 | `mkdir`、`mv`、`cp`、`sed`、`find`、删除自己新建的单个文件等可以用 |

被禁止的命令（见 `AGENTS.md` 红线和 `tools/cards/dispatch.sh` 里的禁令清单）会被拦截并返回错误：换一种办法完成，不要想办法绕过。需要新依赖或新命令，写进报告。

## 7. 总控怎么审（让开发者心里有数）

1. 读 diff：尤其盯卡外文件、被删的测试、被放宽的断言、写死的路径和密钥、新增依赖。
2. 在工作区自己重跑 `web-build`、`web-test`、`rust-fmt`、`rust-check`、`rust-test`，不信自述。
3. 对着验收逐条核对，每一条都要能指出代码位置或运行结果。
4. 涉及界面：合并后在 dev 版里点一遍并截图；涉及数据：在 dev 库副本上跑，不动 dev 库本体。
5. 涉及迁移：用 018 夹具和 dev 库副本各过一遍，确认只追加、不丢行。
6. 跑 `check-scope.sh`：越界改动一律还原，除非卡本身需要改（那就先改卡再合并）。
7. 任何一条过不去就退回，不凑合合并。

## 10. 找方案：`solve_v2` 与 `solve_rerank_v2`（2026-10-05）

### `solve_v2({ query })` → `SolveResult`
本地打分，不联网、不花钱。除原有键外新增 `moreHits`：本地排名 9–16 的后备候选（`SolveHit` 同形状），界面默认不显示，只在 AI 精选从里面点名（最合适 / 合适）时才拿出来；`preselected`、`fullMatchCount`、`gapIntents` 仍然只看前 8（`hits`）。旧后端没有这个键，前端当作空数组。

### `solve_rerank_v2({ request: { query, candidateIds } })` → `RerankResult`（卡 30）
让模型在候选（最多 16 个：`hits` + `moreHits`）里按「能不能做成这件事」重排，并给每个写一句大白话理由。**永远返回 `Ok`**，失败折成 `status`：

| 键 | 含义 |
|---|---|
| `status` | `ok`（刚问过模型）/ `cached`（同一问题 + 同一批候选，用上次的结果，没花 token）/ `skipped`（问题为空、候选不足 2 个、没配置 AI、连续出错暂停中）/ `refused`（额度闸门拒绝：AI 额度是 0、队列暂停、「找方案」AI 精选今天的额度用完）/ `failed`（出错、超时、回复里没有任何合法判断；不重试：一次请求最多等 90 秒，命令最多等 95 秒） |
| `items[]` | 只在 `ok` / `cached` 时非空：`{ repoId, fit, reason }`，按 AI 的顺序（最对口在前）。`fit`：`best`（最多 2 个）/ `good` / `maybe` / `poor`。每个候选正好出现一次；`reason` 已清洗（去 Markdown、链接、内部编号 A1，≤ 60 字） |
| `noneFit` | 清洗后没有任何一个是 `best` / `good`（不信模型自己写的） |
| `note` | AI 的一句话建议（≤ 60 字）；`noneFit` 且模型没写时是「收藏里没有专门做这件事的工具，可以直接交给 Codex 用本机命令完成」 |
| `message` | `skipped` / `refused` / `failed` 时给界面的白话原因 |
| `tokens` | `ok` 是估计的输入 + 输出；`cached` 是 0；别的状态没有 |

- **额度**：走 `spend_guard::solve_rerank`，账本里标 `prompt_version = 'solve-rerank'`，**有自己的额度：每 24 小时最多 30 万 token（约 40 次搜索），且不超过每天额度的一半**（一次性全部整理进行时按 30 万；例如每天额度 10 万，AI 精选最多 5 万），不被后台整理（尤其是全量整理）用掉的额度挡住；前提是 Fox 开过 AI 额度（每天额度大于 0，或一次性全部整理在进行）、队列没暂停。拒绝文案里的「每天 N 的额度」写的是这个有效上限。同一本账，队列和旧功能的「最近 24 小时已用」都看得见它。
- **一次调用一个请求**（卡 34）：一次搜索最多向模型发**一个** HTTP 请求——200 空内容、429、500、3xx、网络错误、超时都不重试、不回退到别的请求、不跟随重定向（reqwest 自带的协议层重试也关掉）；请求体带 `max_tokens = 4096`（OpenAI 兼容和 Anthropic 两条路径都带），整个请求（含读响应体）合计最多等 90 秒，命令最多等 95 秒（比请求略大，工作线程先自己结束）。服务商直接拒绝（4xx、429）、没连上、几秒内的 5xx 把预留整个退回；**等了很久才失败、没拿到可用回复的那一次**（最终超时、等了一阵才回的 5xx、等了一阵才断开、响应体读不完）账本里记 `max(1 万, 提示词估计 + 4096)`（1 万是 `jobs::TIMEOUT_ATTEMPT_TOKEN_ESTIMATE`，提示词最长约 6500 字、估计不到 1 万，所以通常正好是 1 万）。
- **同一问题单飞**：进程内按缓存键（加数据库路径）登记在飞的请求；同一个问题已经有一次在飞，后来的调用不发请求，等先到的那次结束（最多 95 秒）：它成功就返回 `cached`、`tokens = 0`，它失败 / 被拒绝 / 被跳过就返回同样的结果。先到的那次结束（成功、失败、panic）都会清掉登记；清掉之后再来的调用是新的一次。不同问题互不等待。
- **断路器**：进程内按模型名记连续失败次数，只有 `failed`（调用出错、超时、回复看不懂 / 没有合法判断）算；`refused`、`skipped`、`cached` 不算也不清零，一次 `ok` 清零。连续失败 2 次后 10 分钟内直接返回 `skipped`（`AI 精选连续出错，先停 10 分钟，这次按本地排序`），不调模型；10 分钟后放一次进去试（放行时记一份 95 秒的租约：同时进来的别的搜索不能也试；试的这一次没出结果也只占 95 秒），失败从失败那一刻再停 10 分钟，成功清零。读缓存在断路器之前：断路器打开时缓存命中照常返回 `cached`。
- **回复校验**：回复里至少要有一个候选的 `fit` 是认得的写法（`best` / `good` / `maybe` / `poor`），否则（`{}`、编号全对不上、写的都不认得）算 `failed`、不写缓存；部分有效的回复（只给了 `A2: good`）仍然成功，缺的补 `maybe`。理由和建议里出现网址（`://`、`www.`、`foo.com` 这类像域名的写法）整条当作空，走兜底文案。
- **缓存**：表 `solve_rerank_cache`（迁移 036），键 = 提示词版本 + 规范化问题 + 每个候选的 id 与理解卡 `source_hash`；保留最新 300 条。
- **提示词**：`solve-rerank-v2`。核心规则：先想清楚他手里已经有什么、想得到什么——「给……加……」「把……整理成……」「批量……」是加工现成素材，只会从零生成成品的工具最多算 `maybe`。替身模型在六个真实任务上实测：「给短视频加字幕」把「一键生成带字幕的新视频」降到备选以下、把「能导入现成视频并加字幕」的编辑器排第一；「批量去水印」「批量改图尺寸」正确判定收藏里没有专用工具，建议直接交给 Codex。

## 11. 理解卡 v3（2026-10-05，`PROMPT_VERSION = card-v3`）

`card_json` 在 v2 结构上**只追加**了两个键，`card_schema_version` 仍是 2：

| 键 | 含义 |
|---|---|
| `audience` | `business`（不会代码也能用）/ `mixed`（要装软件或改配置，不用写代码）/ `developer`（必须写代码或敲命令）。模型漏写时默认 `mixed` |
| `scenario_evidence` | `{ 场景 slug: 一句 README 或简介里的原话 }`，只留通过核对的标签（原话真的出现在材料里，或场景关键词字面出现） |

核对（`card_pipeline::refine_card`，不花 token）：场景标签必须有依据（`scenario_evidence` 的原话去掉空白后**至少 4 个字符**才算数，太短的什么材料里都有；不够就退到场景关键词字面出现）；平台类（`xhs` / `wx` / `dy`）、自动化（`auto`）、SEO 还要字面出现种子里的 `evidence` 词（README 里要出现至少 2 次，「自动化」这种泛词只认名称 / 描述 / topics）；`audience = developer` 又只剩 `auto` 一个场景就去掉；`maturity = stale` 的去掉全部场景；最多 3 个。没有 README：`what_it_is` 加前缀「只有 GitHub 简介，没有 README：」，`risks` 固定写「没有 README，说明只来自 GitHub 简介」。工具类（app / cli / skill / mcp / api / library / service）的 `risks` 不能空，空就补「README 没写限制，需要自己试」。`one_liner_zh` / `what_it_is` 写成空串或只有空白算缺字段（走修复调用，修不好就失败）；超长截断（`truncate_text`）不会把非空文字截成空，也不留没关的括号。

长度上限：一句话 40 字、说明 160 字、能力 5 条 × 24 字、问题 4 条 × 40 字、时机 3 条 × 50 字、不适合 2 条 × 50 字、注意 3 条 × 50 字、灵感 80 字；超长在句末（其次逗号）断开，不留半截话和没关的括号。README 摘录里「FAQ / 限制 / 免责 / 安全 / 隐私 / 路线图 / 弃用 / 费用 / 系统要求」小节另给 1200 字额度（总上限 7700）。

**旧卡**：提示词版本不是 `card-v3` 的卡算「说明过期」（`Outdated` 范围；「一次性全部整理」要数的「还要整理多少」也含它），已确认（`review_status = confirmed`）的不碰。

### 场景规则（`scenarios.rs` + `docs/rebuild/spec/scenarios_seed.json` v2）
规则只读仓库自己写的名称、描述、topics 和 README 开头 1500 字，**不再读 AI 写的中文说明 / 关键词 / 能力 / 分类名**；命中名称 / 描述 / topics 里的一个词，或 README 里两个不同的词，才算候选；要求证据的场景（`evidence` / `evidence_meta` 非空）README 里的命中不单独成立。种子里每个场景的 `description_zh` 是「给 / 不给」口径，原样放进理解卡提示词。启动时 `audit_scenario_tags` 把库里已有的、没有证据的 AI / 规则建议删掉（Fox 确认 / 拒绝过的、用户自己加的不碰）；种子（关键词、口径）更新时旧的规则建议按新规矩重做一遍。
